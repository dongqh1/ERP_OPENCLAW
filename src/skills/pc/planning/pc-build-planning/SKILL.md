# PC 配置规划

## 输入提取

从当前会话提取：预算、用途/游戏/AI 任务、分辨率、目标帧率、新旧偏好、硬性显存或型号要求、已有部件。

- 用户已有/明确保留的部件写入 `keep_components`，`owned=true`，不得替换且不计入本次新购金额。
- 用户只是点名“想要某型号”时，作为待购部件处理，`owned=false`。
- 用户明确提出显卡显存下限时，把下限传入优化器参数 `min_gpu_vram_gb`，不能只靠自然语言提醒子 Agent。
- 用户明确接受低于原显存下限的指定方案后，按用户同意的新下限继续，并在最终答复标出原要求与妥协值。
- 用户没有给预算时先只追问预算。其他字段按已知信息规划，并把默认假设写清楚；只有硬性条件相互冲突时才继续追问。
- 用户给出的硬条件不能当作普通偏好优化掉。若目录无解，解释哪个条件冲突，并列出可选择的放宽方向。

## 生成与校验

1. 确认候选目录记录，必要时用 `hardware_detail` 补齐参数。
2. 调用 `pc_budget_optimizer`，传入预算、用途、分辨率、目标帧率、`min_gpu_vram_gb`（若用户给出）、新旧偏好和 `keep_components`。
3. 检查返回的每个部件是否符合用户硬条件、全部必需类别是否齐全、新购金额是否不超预算。
4. 将最终清单交给 `pc_compatibility_check` 独立核验；逐条报告工具返回的检查项，不能扩大检查范围。
5. 若核验失败，按失败原因调整一次候选并重新核验；仍失败就报告无可行配置，不要把失败结果写成通过。

## 回答格式

用表格列出类别、型号、关键规格、模拟目录价格、新旧状态及选择理由；区分“目录合计”“新购金额”和“预算余额”。列出兼容性检查摘要和未满足的硬条件。

## 禁止过度推断

- 不得把模拟分数解释为真实游戏 FPS、AI 训练速度、瓶颈结论或性价比排名。
- 不能仅凭显卡品牌断言 CUDA/ROCm 的当前兼容性，也不能仅凭“显存容量”承诺某模型一定可训练；没有官方来源或实测数据时要说清楚。
- `compatible=true` 仅代表 Java 服务列出的检查通过；不代表所有 BIOS、散热、噪声、机箱接口和软件环境均已验证。
- 不得把模拟目录总价称为“市场参考价”或“当前价”。
